--n-cpu-ffn / --cpu-ffn 実装・実測レポート（Qwen3.8-27B / RX 7800 XT）

2026-08-22 · LlamaDock (llama-tq3) · PR ggml-org/llama.cpp#26622 (John-194) を AtomicBot フォークへ適用

1. 目的

Dense モデルの FFN 重みだけをシステム RAM へオフロードする新オプション --n-cpu-ffn / -cffn (--cpu-ffn) を AtomicBot (TurboQuant fork) に導入し、16GB VRAM 環境での速度・実用性を Qwen3.8-27B 系で実測検証する。 Reddit の報告（「Qwen3.8 27B Q4_K_M が約 20 tok/s」）が本環境で再現するかを確認。

5. 考察

  • Reddit の「約 20 tok/s」は本環境では非再現。 Dense FFN の CPU オフロードは毎トークン全 FFN を DDR5 帯域経由で計算するため tg が帯域律速になり、RX 7800 XT + DDR5 では -ncffn 16 で −65%、全オフロードで −88〜91%。CUDA+高速メモリ前提の主張と理論的に整合しないため条件差が大きいと判断。
  • pp への影響は軽微（R3 −29% / R4 −9〜68%程度まで幅あり）。プロンプト処理は op-offload（CPU 側重みの一括 GPU ストリーミング）が働くため。長コンテキスト投入主体の用途なら実害は小さい。
  • 本オプションの正しい使い道は「速度ではなく VRAM 余剰化」。 IQ4_XS(14.6GiB) はフルGPUで KV/計算バッファの余地がほぼ無いが、例えば -ncffn 24 程度で数 GB 空ければ 32k→65k コンテキスト拡張が可能になる。速度より文脈長が必要な場合の選択肢として GUI スキーマ（cpu_ffn/n_cpu_ffn、追加済み）から利用する価値がある。
  • 副次発見: HauhauCS IQ4_XS がフルGPUで tg 29.0 t/s / pp 544 t/s。 理論帯域上限（624 GB/s ÷ 14.6GiB ≈ 42 t/s）に対し ~70% 効率。IQ3_M が 16.9 t/s に留まったのは i-quant カーネルが RDNA3 で不利なためで、前回レポートの「IQ 系カーネル未最適」所見と整合。dense 27B を 16GB で回すなら IQ4_XS 一択。
